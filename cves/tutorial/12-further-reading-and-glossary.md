# Further Reading and Glossary

Two kinds of material are collected here. The first is an annotated bibliography: the external sources that actually repay the time spent on them, grouped by what they are for rather than by publication date. The second is a glossary of the vocabulary used across the preceding eleven sections, with the instrument you would use to observe each thing on a real device wherever one exists.

A word on how to read the bibliography. Kernel exploitation literature ages unevenly. A 2007 description of how SLUB organizes a slab is still accurate because the data structures barely moved; a 2013 description of what KASLR defends against is still accurate as a threat model but describes an implementation two rewrites ago; a 2017 exploit writeup may depend on a heap layout that three mitigations have since invalidated while its reasoning remains exemplary. Entries below say so where the distinction changes what you should take from the source.

## Vulnerability records and the Android trees

The kernel has been its own CVE Numbering Authority since February 2024, and its own policy document explains the consequences better than any secondary account: [Documentation/process/cve.rst](https://docs.kernel.org/process/cve.html) states that assignment happens only after a fix exists and is tracked "by the git commit id of the original fix". [LWN's coverage of the process](https://lwn.net/Articles/978711/) supplies the context — volume, disagreement, and what maintainers actually do. The machine-readable record set is the kernel's own vulnerabilities repository at [kernel.googlesource.com/pub/scm/linux/security/vulns](https://kernel.googlesource.com/pub/scm/linux/security/vulns/), and the announcement stream is [linux-cve-announce](https://lore.kernel.org/linux-cve-announce/). Clone the first, poll the second; both are more useful than NVD because both give you commit ids instead of version ranges.

For Android specifically, the [Android Security Bulletin index](https://source.android.com/docs/security/bulletin) lists every monthly bulletin back to 2015, and any individual bulletin such as [September 2025](https://source.android.com/docs/security/bulletin/2025-09-01) shows the structure: two patch levels a month, CVE plus `A-`-prefixed bug id plus a link to the fix where it is public. The tree those fixes land in is described by [Android common kernels](https://source.android.com/docs/core/architecture/kernel/android-common) and browsable at [android.googlesource.com/kernel/common](https://android.googlesource.com/kernel/common/); the split between generic core and vendor modules is [Generic Kernel Image](https://source.android.com/docs/core/architecture/kernel/generic-kernel-image), whose promise of a stable KMI within an LTS is exactly what makes a single set of struct offsets usable across a family of devices, and [GKI versioning](https://source.android.com/docs/core/architecture/kernel/gki-versioning) explains the release-name encoding you will read off a device banner.

On a device, that banner is one command away, and it is the only claim about the kernel that is not somebody's metadata:

```
adb shell cat /proc/version
adb shell getprop ro.build.version.security_patch
```

The first prints the ACK branch and the `-g<sha>` of the build; the second prints the patch level the vendor asserts. A disagreement between them is a triage lead, not a bug in the tools — [01-vulnerability-discovery-and-patch-triage.md](01-vulnerability-discovery-and-patch-triage.md) works through what to do about it.

## Kernel documentation worth reading end to end

Kernel documentation is uneven, but the following pages are current, authoritative, and directly load-bearing for exploitation work.

Memory. [Physical memory](https://docs.kernel.org/mm/physical_memory.html) explains nodes, zones, `struct page` and the buddy allocator's `free_area`; [the arm64 memory layout](https://docs.kernel.org/arch/arm64/memory.html) explains the address-space split, translation-table depth and what a 39- versus 48-bit VA space does to your pointers. [The slab allocator's users guide](https://docs.kernel.org/admin-guide/mm/slab.html) covers the debug options, their per-cache selectors and the out-of-tree `slabinfo` tool; it is one document that has been renamed and moved, so read the switch it describes as `slab_debug` on current kernels and `slub_debug` on the 6.1-era ACK builds this tutorial targets. [The pagemap documentation](https://docs.kernel.org/admin-guide/mm/pagemap.html) specifies the 64-bit-per-page entry format — PFN in bits 0–54, present in bit 63 — and states that the PFN reads back as zero without `CAP_SYS_ADMIN`.

Observation. [kprobes](https://docs.kernel.org/trace/kprobes.html) describes the mechanism, [kprobe-based event tracing](https://docs.kernel.org/trace/kprobetrace.html) describes the text interface you actually type, and [ftrace](https://docs.kernel.org/trace/ftrace.html) describes the tracefs files everything else is built on (`current_tracer`, `trace`, `trace_pipe`, `tracing_on`, the per-CPU buffers). [BTF](https://docs.kernel.org/bpf/btf.html) specifies the type-information format that makes struct layouts recoverable from a running kernel you cannot rebuild.

Postmortem. [ramoops](https://docs.kernel.org/admin-guide/ramoops.html) documents the persistent-store backend that survives a panic-reboot, which on Android is the difference between having a backtrace and guessing; [bug hunting](https://docs.kernel.org/admin-guide/bug-hunting.html) documents how to turn an oops into a source line. [KASAN](https://docs.kernel.org/dev-tools/kasan.html) and [KFENCE](https://docs.kernel.org/dev-tools/kfence.html) document the sanitizers, including which of them can run on production hardware.

Policy and privilege. [Credentials in Linux](https://docs.kernel.org/security/credentials.html) is David Howells' description of `struct cred`, the real/effective/saved/filesystem quadruple and the rule that a committed cred is immutable — the rule an exploit breaks. [capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html) enumerates the permitted, effective, inheritable, bounding and ambient sets. [The LSM index](https://docs.kernel.org/admin-guide/LSM/index.html) lists the modules and the "at most one major module" rule, and [seccomp filtering](https://docs.kernel.org/userspace-api/seccomp_filter.html) documents the return actions in precedence order, which is what tells you whether a blocked syscall kills you, traps you or just returns an errno. [The kernel sysctl guide](https://docs.kernel.org/admin-guide/sysctl/kernel.html) is where `kptr_restrict`, `dmesg_restrict` and `perf_event_paranoid` are defined; those three values determine most of what an unprivileged process can see.

Android's own security documentation completes the picture: [SELinux on Android](https://source.android.com/docs/security/features/selinux) for domains and enforcing mode, [binder IPC](https://source.android.com/docs/core/architecture/hidl/binder-ipc) for the three binder domains and their SELinux gating, and [the boot image header](https://source.android.com/docs/core/architecture/bootloader/boot-image-header) for the container your target kernel actually ships in.

## Long-running research blogs

[Google Project Zero](https://projectzero.google/) is the single highest-yield source, both for technique and for how to write up technique. Its [public bug tracker](https://project-zero.issues.chromium.org/savedsearches/7162405) carries the full report for each disclosed issue, often including the PoC; the [0day "In the Wild" programme page](https://projectzero.google/0day.html), which introduces and links the tracking spreadsheet, and the companion [root-cause analyses](https://googleprojectzero.github.io/0days-in-the-wild/rca.html) are the best available census of what attackers actually deploy. Four posts in particular are worth reading as models: [Bad Binder](https://projectzero.google/2019/11/bad-binder-android-in-wild-exploit.html) on an in-the-wild Android kernel UAF, [Mind the Gap](https://projectzero.google/2022/11/mind-the-gap.html) on the Mali GPU driver and the patch-gap problem, [Exploiting null-dereferences in the Linux kernel](https://projectzero.google/2023/01/exploiting-null-dereferences-in-linux.html) on turning an allegedly unexploitable bug class into a primitive, and [Analyzing a modern in-the-wild Android exploit](https://projectzero.google/2023/09/analyzing-modern-in-wild-android-exploit.html). [Exploiting the Linux kernel via packet sockets](https://projectzero.google/2017/05/exploiting-linux-kernel-via-packet.html) (2017) is historically important and its heap layout assumptions are dated, but it remains one of the clearest expositions of turning an integer problem into a controlled overflow.

Independent researchers who publish reproducible work, with a representative post each:

- Alexander Popov's [Some notes on the security properties of the pipe_buffer kernel object](https://a13xp0p0v.github.io/2026/04/20/pipe-buffer-experiments.html), on measurement-driven heap work, and, as reference material, his [Linux Kernel Defence Map](https://github.com/a13xp0p0v/linux-kernel-defence-map), a graph of which mitigation blocks which technique.
- Will's Root's [Reviving Exploits Against Cred Structs](https://www.willsroot.io/2022/08/reviving-exploits-against-cred-struct.html), subtitled "Six Byte Cross Cache Overflow to Leakless Data-Oriented Kernel Pwnage", which is the cross-cache reference in this list: a six-byte overflow carried through a page-granularity reuse into a data-only escalation with no leak. Separately, [corCTF 2021 Fire of Salvation](https://www.willsroot.io/2021/08/corctf-2021-fire-of-salvation-writeup.html) is `msg_msg` as an elastic object — arbitrary read through `MSG_COPY`, arbitrary write through a copy paused with `userfaultfd`. That second one depends on unprivileged `userfaultfd`, now gated (see the LWN entry below); the elastic-object reasoning survives the gating, the recipe does not.
- Vitaly Nikolenko's duasynt notes on [kernel heap spraying](https://duasynt.com/blog/linux-kernel-heap-spray) and [heap feng shui](https://duasynt.com/blog/linux-kernel-heap-feng-shui-2022), which are unusually explicit about which allocation sites are still usable.
- syst3mfailure's [An RBTree Family Drama](https://syst3mfailure.io/rbtree-family-drama/), a kernelCTF writeup taking CVE-2025-38001 — a use-after-free in the HFSC packet scheduler, reached by preventing dequeue with a rate-limited TBF root qdisc — from the fuzzer crash to a page-level data-only chain with a success rate near 100% across four distribution kernels. More long-form writeups at [syst3mfailure.io](https://syst3mfailure.io/).
- notselwyn's [Flipping Pages](https://pwning.tech/nftables/) on CVE-2024-1086 in `nf_tables`, which introduces the Dirty Pagedirectory technique, and Interrupt Labs' [pipe_buffer arbitrary read write](https://www.interruptlabs.co.uk/articles/pipe-buffer) on `pipe_buffer` as a universal target.
- [Exodus Intelligence](https://blog.exodusintel.com/2022/12/19/linux-kernel-exploiting-a-netfilter-use-after-free-in-kmalloc-cg/) on exploiting in `kmalloc-cg`, which is the concrete answer to "the accounted caches broke my spray".
- [Dirty Pipe](https://dirtypipe.cm4all.com/) (Max Kellermann, CVE-2022-0847), the best short example of a root-cause narrative written by the person who found it, and [Dirty Pagetable](https://yanglingxi1993.github.io/dirty_pagetable/dirty_pagetable.html), which generalizes page-table corruption into a reusable technique.
- Lexfo's CVE-2017-11176 series, which runs to four parts: start at [part 1](https://blog.lexfo.fr/cve-2017-11176-linux-kernel-exploitation-part1.html), where the bug is found and reached, and finish at [part 4](https://blog.lexfo.fr/cve-2017-11176-linux-kernel-exploitation-part4.html), the SMEP bypass and the ROP chain. It is the most patient beginner-to-working-exploit walkthrough in existence; the target kernel is old and several of its primitives are gone, the method is not.
- [An introduction to exploit reliability](https://blog.isosceles.com/an-introduction-to-exploit-reliability/) is the piece to read before claiming a success rate.

For breadth, [xairy/linux-kernel-exploitation](https://github.com/xairy/linux-kernel-exploitation) is a curated, regularly updated index of papers, articles, exploits and tools maintained by Andrey Konovalov; when you need to know whether a technique has prior art, start there rather than with a search engine.

## LWN, for the defenders' account of the same mechanisms

LWN explains kernel internals from the point of view of the people changing them, which is exactly the perspective an exploit developer lacks. [The SLUB allocator](https://lwn.net/Articles/229984/) (2007) describes the design decisions — per-CPU structures, metadata in the page descriptor, cache merging — that still determine how a spray behaves. [What is RCU, Fundamentally?](https://lwn.net/Articles/262464/) by Paul McKenney is the prerequisite for the two deferral mechanisms that decide when a cross-cache attempt's page actually moves, and they are not the same mechanism: an object-level `call_rcu()` postpones the `kmem_cache_free()` itself into a callback, so nothing has been freed yet in the interval, whereas a cache carrying `SLAB_TYPESAFE_BY_RCU` hands the object slot back for reuse immediately and defers only the slab page's return. [06-cross-cache-attacks.md](06-cross-cache-attacks.md) separates the two against the target kernel's own source. [Kernel address space layout randomization](https://lwn.net/Articles/569635/) (2013) is dated as implementation but exact as threat model, including the observation that KASLR's value collapses the moment any pointer leaks. [A new LLVM CFI implementation](https://lwn.net/Articles/898040/) describes kCFI's per-prototype hash check at function entry, which is why an arbitrary indirect call is no longer a plan on an Android kernel, and [hypervisor kCFI for arm64](https://lwn.net/Articles/977761/) shows the same scheme extended to EL2. [Control over userfaultfd kernel-fault handling](https://lwn.net/Articles/835373/) documents the restriction that removed the most convenient race-widening primitive from unprivileged reach. [A kernel debugger in Python: drgn](https://lwn.net/Articles/789641/) introduces the tool you will use to check your own reasoning against a live kernel.

## kernelCTF and other complete, modern exploits

The shortest path to seeing a full modern exploit — 0-day, LTS kernel, mitigations on, measured stability — is Google's kernelCTF. [The programme rules](https://google.github.io/security-research/kernelctf/rules.html) require a submission to reach a minimum stability across twenty runs and to complete within a time limit per run, and require public release of the exploit within 90 days. The consequence is a growing public corpus: [pocs/linux/kernelctf](https://github.com/google/security-research/tree/master/pocs/linux/kernelctf) contains per-submission directories with source, build instructions and documentation, frequently against mitigation-hardened instances. Read them for the parts that writeups usually omit: the retry loops, the pre-flight checks, the bail-out conditions. Google's older [CVE-2021-22555 writeup](https://google.github.io/security-research/pocs/linux/cve-2021-22555/writeup.html) remains an excellent single-file exposition of turning a two-byte overflow into root.

Academic work that is genuinely operational rather than taxonomic, each cited by title so the claim can be checked without opening the link:

- [DirtyCred](https://zplin.me/papers/DirtyCred.pdf) (Lin et al., CCS 2022), which reframes escalation as object swapping and thereby sidesteps KASLR entirely.
- [SLUBStick](https://www.usenix.org/conference/usenixsecurity24/presentation/maar-slubstick) (Maar et al., USENIX Security 2024), on converting a slab-level flaw into page-table control with high reliability.
- [When Good Kernel Defenses Go Bad](https://www.usenix.org/conference/usenixsecurity25/presentation/maar-kernel) (Maar et al., USENIX Security 2025), subtitled "Reliable and Stable Kernel Exploits via Defense-Amplified TLB Side-Channel Leaks": the defences themselves amplify a TLB side channel that leaks where heap objects sit.
- [Pspray](https://www.usenix.org/conference/usenixsecurity23/presentation/lee-yoochan) (Lee et al., USENIX Security 2023), a timing side channel that tells you which allocation landed on a fresh slab, raising heap-exploit success rates from roughly 56% to roughly 98%.
- [Take a Step Further: Understanding Page Spray in Linux Kernel Exploitation](https://www.usenix.org/conference/usenixsecurity24/presentation/guo-ziyi) (Guo et al., USENIX Security 2024), the systematic account of page-level spraying and the DIRTYPAGE model.
- [KOOBE](https://www.usenix.org/conference/usenixsecurity20/presentation/chen-weiteng) (Chen et al., USENIX Security 2020) on extracting exploit capabilities automatically from out-of-bounds writes, and [SyzScope](https://www.usenix.org/conference/usenixsecurity22/presentation/zou) (Zou et al., USENIX Security 2022) on turning a fuzzer's apparently low-risk bug report into an assessed security impact. Read together they are the state of automated exploitability reasoning, which is still weakest exactly where an Android chain is hardest: reachability from a confined domain.

Conference material worth the download: [USMA: Share Kernel Code](https://i.blackhat.com/Asia-22/Thursday-Materials/AS-22-YongLiu-USMA-Share-Kernel-Code-wp.pdf) (Black Hat Asia 2022) on abusing user-mapped kernel pages, [bad_io_uring](https://i.blackhat.com/BH-US-23/Presentations/US-23-Lin-bad_io_uring-wp.pdf) (Black Hat USA 2023) on a modern subsystem-specific chain, and NCC Group's notes on [Exploit Engineering: Attacking the Linux Kernel](https://www.nccgroup.com/au/research-blog/offensivecon-2023-exploit-engineering-attacking-the-linux-kernel/) from OffensiveCon 2023. [OffensiveCon](https://www.offensivecon.org/) is the single-track conference whose kernel track is most consistently worth following year to year.

## Fuzzing infrastructure

[syzkaller](https://github.com/google/syzkaller) is the coverage-guided kernel fuzzer whose output dominates the modern kernel CVE stream; its `docs/` directory is the practical manual, and [docs/syzbot.md](https://github.com/google/syzkaller/blob/master/docs/syzbot.md) explains the automated instance. The [syzbot dashboard](https://syzkaller.appspot.com/upstream) is worth treating as a vulnerability feed in its own right: it publishes crash reports, reproducers and bisection results before, and sometimes instead of, any CVE. Two practical habits — filter by subsystem to find the areas whose bugs match your reachable attack surface, and read the C reproducer rather than the syz one, because the C reproducer tells you which syscalls an unprivileged process actually needs.

## Books and courses

[The Linux Programming Interface](https://man7.org/tlpi/) (Kerrisk, No Starch, 2010) is the reference for the userspace side of every syscall you will abuse; the kernel has moved, the interface contracts largely have not. [Is Parallel Programming Hard, And, If So, What Can You Do About It?](https://mirrors.edge.kernel.org/pub/linux/kernel/people/paulmck/perfbook/perfbook.html) (McKenney, free, continuously updated) is the source for RCU, memory ordering and why a race window has the shape it does. [Android Security Internals](https://nostarch.com/androidsecurity) (Elenkov, No Starch, 2014) predates most of the current framework, but its account of the permission model, package management and the uid-per-app design is still the clearest explanation of why Android's userspace boundaries sit where they do. *A Guide to Kernel Exploitation: Attacking the Core* (Perla and Oldani, Syngress, 2010) is the historical textbook — every specific technique in it is obsolete, and its framing of the problem is not; it is catalogued in xairy's collection along with more current alternatives.

For structured practice, [pwn.college](https://pwn.college/) (Arizona State University, free) builds the memory-corruption and systems fundamentals that kernel work assumes, with a hands-on dojo per topic. [Xairy Labs](https://xairy.io/trainings/) runs paid multi-day courses specifically on Linux and Android kernel exploitation, including labs on current Pixel hardware; the public collection linked above is the free counterpart.

## Verifying a definition on your own kernel

The glossary below is deliberately terse. Every structural claim in it can be checked against your own target, and the checking is the part that matters, because the numbers differ per build. What follows is a reference card — one invocation per instrument, the privilege it needs, and the section that teaches it properly. Sample outputs are from panther (Pixel 7, `6.1.157-android14-11-gbd23337e42e7-ab14791245`, build `CP2A.260705.006`), the target this project measures against; where a block shows the *shape* of the output rather than a capture, it says so.

Which instruments exist at all. That is a configuration question, and it is answered first, because it decides whether any of the rest is available. `CONFIG_IKCONFIG_PROC=y` is set in the [arm64 `gki_defconfig` for `android14-6.1`](https://android.googlesource.com/kernel/common/+/refs/heads/android14-6.1/arch/arm64/configs/gki_defconfig), and `kernel/configs.c` creates the file at mode 0444, so this is an unprivileged one-liner:

```
adb shell zcat /proc/config.gz | grep -E 'DEBUG_INFO_BTF|SLUB_DEBUG|SLAB_MERGE|SLAB_FREELIST|KASAN|PROC_KCORE|IKCONFIG'
```

On the target that returns `CONFIG_DEBUG_INFO_BTF=y` (BTF is embedded), `# CONFIG_SLAB_MERGE_DEFAULT is not set` (nothing merges), `CONFIG_SLAB_FREELIST_HARDENED=y` and `CONFIG_SLAB_FREELIST_RANDOM=y` (freelist pointers obfuscated, initial free order shuffled), `CONFIG_KASAN=y` with `CONFIG_KASAN_HW_TAGS=y` (MTE-based KASAN compiled in, inert unless the command line enables it), and `CONFIG_PROC_KCORE` unset, which is why drgn cannot attach to the phone. Where `/proc/config.gz` is absent, the fallback is the published `gki_defconfig` for the branch named in `/proc/version`; that is a claim about the branch, not about the shipped build, and should be labelled as such wherever it is used. Sections [01](01-vulnerability-discovery-and-patch-triage.md), [04](04-kaslr-and-information-leaks.md), [05](05-heap-grooming-and-spraying.md), [09](09-privilege-escalation-to-root.md) and [10](10-survivability-and-measurement.md) each run this against their own option set.

Struct layouts, without source and without rebuilding. Modern Android GKI kernels ship BTF type information in the running kernel. Pull it and read it with the dwarves suite; `-F btf` forces the BTF reader, which a raw blob with no ELF sections needs:

```
adb pull /sys/kernel/btf/vmlinux ./vmlinux.btf
pahole -F btf -C cred ./vmlinux.btf
```

The output is a C struct declaration with an offset-and-size comment on every member and an explicit note for padding holes. On the target build:

```
struct cred {
        atomic_t                   usage;                /*     0     4 */
        kuid_t                     uid;                  /*     4     4 */
        kgid_t                     gid;                  /*     8     4 */
        ...
        unsigned int               securebits;           /*    36     4 */
        kernel_cap_t               cap_inheritable;      /*    40     8 */
        ...
        void *                     security;             /*   120     8 */
        ...
        /* size: 176, cachelines: 3, members: 26 */
```

Those are the numbers [09-privilege-escalation-to-root.md](09-privilege-escalation-to-root.md) uses and the ones encoded in this project's `cves/lib/root/cred.h` as `CRED_UID_OFF 4`, `CRED_SECUREBITS_OFF 36`, `CRED_SECURITY_OFF 120`. Run the same command on a 7.x host and the member list is identical but `usage` is an `atomic_long_t`, so it occupies eight bytes rather than four, `uid` sits at 8, every identity field after it has moved, and the trailer reads `size: 184`. One field's type changed and the entire identity block shifted. That is the whole argument for deriving the number per build instead of copying it out of a writeup.

What you may legitimately conclude: the offset of `uid` within `struct cred` on this exact build. What you may not conclude: that the same offset holds on any other build, including the next monthly update of the same device. If `pahole` is unavailable, `bpftool btf dump file vmlinux.btf format c` emits the entire type universe as compilable C, which you can grep or feed to a compiler that computes `offsetof` for you.

BTF's limits are worth stating precisely, because a wrong version of them will make you abandon a type that is there. BTF carries types, not addresses: it gives no symbol value, which is why it complements `/proc/kallsyms` rather than replacing it. It is encoded from the built vmlinux's debug information, so it covers what that image contains — a type compiled out by config is genuinely absent, but a type that no exported function mentions is not; `pahole -C task_security_struct` and `pahole -C slab` both resolve. And it is per-image: a vendor module's types live in a separate blob at `/sys/kernel/btf/<module>`, which is where a GKI driver's structs are found. On privilege, `/sys/kernel/btf/vmlinux` is mode 0444, but DAC is not the only gate — SELinux may deny the read from `shell` or an app domain on a production device, in which case the blob comes from the public GKI build artifact matching the banner or from the boot image. [10](10-survivability-and-measurement.md) covers the export mechanism and [09](09-privilege-escalation-to-root.md) the off-device routes.

Slab cache inventory. `/proc/slabinfo` exists only where the build sets `CONFIG_SLAB` or `CONFIG_SLUB_DEBUG`, since the whole block in `mm/slab_common.c` sits under `#if defined(CONFIG_SLAB) || defined(CONFIG_SLUB_DEBUG)`. Inside that block `SLABINFO_RIGHTS` is 0600 under `#ifdef CONFIG_SLAB` and 0400 otherwise — the write bit belongs to the SLAB allocator's tunable-writing interface, not to SLUB debugging — so on a SLUB kernel, which is every GKI target, the file is mode 0400: root-readable and never writable. `No such file or directory` and `Permission denied` are therefore different answers, the first saying the build exposes no slab statistics at all and the second saying the file is there and you are not root; [06-cross-cache-attacks.md](06-cross-cache-attacks.md) carries the source reading. The shape of the output, not a capture, since the counts move between two consecutive reads:

```
adb shell su -c 'head -3 /proc/slabinfo'
# slabinfo - version: 2.1
# name            <active_objs> <num_objs> <objsize> <objperslab> <pagesperslab> : ...
kmalloc-256           2624       2656        256          32            2 : ...
```

`objsize` and `pagesperslab` give the cache geometry that determines how many objects you must free to release a page. `slabtop -o -s c` sorts the same data by cache size for a live view. [05-heap-grooming-and-spraying.md](05-heap-grooming-and-spraying.md) carries the richer per-cache view under `/sys/kernel/slab/<cache>/` — `object_size`, `objs_per_slab`, `order`, `cpu_partial`, `min_partial` — and what each of those decides.

Merging has its own shape and, on this target, its own answer. `aliases` and the rest of `/sys/kernel/slab/<cache>/` sit inside the `CONFIG_SYSFS` block of `mm/slub.c`, not under `CONFIG_SLUB_DEBUG`, and are declared `SLAB_ATTR_RO`, which expands to `__ATTR_RO_MODE(_name, 0400)`. Reading a value therefore needs root; the symlinks themselves do not.

```
adb shell su -c 'cat /sys/kernel/slab/kmalloc-256/aliases'   # a count: s->refcount - 1
adb shell 'ls -l /sys/kernel/slab | grep ":"'                # e.g. AF_VSOCK -> :A-0001280
```

`aliases` is a count, not a list. The listing is where the merge sets are. `sysfs_slab_add()` gives every mergeable cache a `create_unique_id()` directory named `:`, then a letter per merge-relevant flag (`d`, `D`, `a`, `F`, `A`), then the object size in seven digits, and symlinks each merged cache's name at it; so `:A-0001280` is the set of `SLAB_ACCOUNT` caches of size 1280, and every name pointing there shares one `kmem_cache` and therefore one freelist. Out of tree, `slabinfo -a` (built from `tools/mm/slabinfo.c`) prints the same sets directly.

On a stock GKI device, expect none of it. The arm64 `gki_defconfig` for `android14-6.1` carries `# CONFIG_SLAB_MERGE_DEFAULT is not set`, so no cache merges and `aliases` reads 0 unless `slab_merge` was passed on the kernel command line. `zcat /proc/config.gz | grep SLAB_MERGE` is the check, and [05](05-heap-grooming-and-spraying.md) develops what an unmerged allocator does to spray-vehicle selection.

Page-allocator state. `/proc/buddyinfo` is mode 0444 and needs nothing; `/proc/pagetypeinfo` is mode 0400 and needs root. Both modes are set in the `proc_create_seq()` calls in `mm/vmstat.c`. Shape, again, rather than a capture:

```
adb shell cat /proc/buddyinfo
Node 0, zone   Normal   3812   1204    517    198     76 ...
```

Each column is the count of free blocks of order 0, 1, 2 and upward in that zone. Sampled before and after a free, it tells you whether a slab page actually returned to the buddy allocator or merely went onto a per-CPU list. `/proc/pagetypeinfo` splits exactly those counts by migratetype, which is what decides reachability rather than merely order: a reclaim spray built from movable anonymous pages does not compete for an unmovable slab page however well the order matches, and pagetypeinfo is where you see whether the order you care about is even on an unmovable free list. `/proc/zoneinfo` adds the zone's watermarks and the per-CPU pageset `count`, `high` and `batch`. [06-cross-cache-attacks.md](06-cross-cache-attacks.md) uses the three together.

Reading memory at a probe point. Where tracefs is writable, a kprobe is an observation instrument and, at a known address, a read. Neither of its two failure modes announces itself in the trace output, so the recipe carries the two checks that make its answer falsifiable:

```
echo > /sys/kernel/tracing/trace                      # start from an empty buffer
echo 'p:peek0 <rare_symbol> val=@0xffffffc0xxxxxxxx:u64 chk=@0xffffffc0yyyyyyyy:u64' \
    > /sys/kernel/tracing/kprobe_events
echo 1 > /sys/kernel/tracing/events/kprobes/peek0/enable
echo 1 > /sys/kernel/tracing/tracing_on
# ... now make something call <rare_symbol> ...
cat /sys/kernel/tracing/trace           # ... peek0: (<rare_symbol>+0x0/0x...) val=0x... chk=0x...
cat /sys/kernel/tracing/kprobe_profile  # "  peek0   <nhit>   <nmissed>" — nhit must be nonzero
echo 0 > /sys/kernel/tracing/events/kprobes/peek0/enable
echo > /sys/kernel/tracing/kprobe_events
```

The two failures are distinct and each has its own check. The first is that the probe never fired: there is no record at all, which is a statement about reachability and not about the memory. `kprobe_profile` settles that one — until `nhit` for `peek0` is nonzero, nothing in `trace` is evidence about the address. The second is that the probe fired and the fetch faulted. `store_trace_args()` in `kernel/trace/trace_probe_tmpl.h` calls `process_fetch_insn()` and uses its return value only for a dynamic argument; for a fixed-size fetch the value is discarded, and `process_fetch_insn_bottom()` returns the fault from its dereference stage before reaching the store stage, so the argument's slot in the reserved ring-buffer record is never written and the line prints whatever bytes that slot already held. On a buffer you have just cleared those bytes are usually zero, which is how a faulting fetch most often presents; on a buffer with traffic in it they are a stale value from an earlier record and look like a plausible result. An unmapped address, a mistyped address and a genuine read are therefore indistinguishable from the value alone. Hence `chk=`: a second fetch in the same probe aimed at an address whose contents you already know — a symbol with a fixed value — so a record whose `chk` is wrong is visibly garbage rather than silently garbage. The two checks do not substitute for each other. `nhit` separates "never reached" from "read"; `chk=` separates "read" from "faulted". Take two reads and require them to agree before using either. [04-kaslr-and-information-leaks.md](04-kaslr-and-information-leaks.md) has the full four-step sequence, the `comm` filter and the choice of probe site.

Three further properties bite in practice. The probe fires only when the probed function runs, so the site must be one the process you control is certain to enter and rare enough that its record is not buried; `vfs_read` fails the second test, firing thousands of times a second. Clear `trace` before arming, or you will read a stale buffer — which is also the condition under which a faulted fetch prints something other than zero. And always clear `kprobe_events` afterwards, because a probe left armed changes the timing of everything measured after it. Some builds reject the explicit type suffix on an absolute-address fetch, in which case drop `:u64`. [09-privilege-escalation-to-root.md](09-privilege-escalation-to-root.md) has the other half of this — choosing a function only your own process calls, and filtering to it — and [10-survivability-and-measurement.md](10-survivability-and-measurement.md) treats the result as a measurement rather than an assertion. Write access to tracefs on Android generally means root or a specifically permissive policy; [03-crash-triage-and-root-cause-analysis.md](03-crash-triage-and-root-cause-analysis.md) covers the postmortem alternative when it is unavailable.

Walking live structures. [drgn](https://drgn.readthedocs.io/en/latest/) turns a kernel into a Python object graph:

```
drgn -k
>>> prog['init_task'].comm
>>> [t.comm.string_().decode() for t in for_each_task(prog)][:5]
```

The prerequisite chain is the point, and it rules the phone out. `drgn -k` reads the live kernel through `/proc/kcore`, which needs `CONFIG_PROC_KCORE`; that symbol does not appear in the arm64 `gki_defconfig`, so drgn cannot attach to a stock Pixel at all. It also needs root and either DWARF or BTF, and GKI release images ship no DWARF. The snippet above therefore runs against a crash dump, a Cuttlefish instance, or a lab kernel built to match — never the target. [crash](https://crash-utility.github.io/) does the same for a captured dump. Their role is to establish ground truth on a machine where you already have privilege, so an unprivileged primitive's answers can be checked against a known-correct one; [05](05-heap-grooming-and-spraying.md) and [09](09-privilege-escalation-to-root.md) place them in the workflow.

Policy. `getenforce` prints `Enforcing` or `Permissive`; `id -Z` prints your own security context; `ls -Z /dev/uhid` prints the label of a device node. Those three work as shell with no privilege and answer most reachability questions on their own. Rule-level queries need the binary policy, and `/sys/fs/selinux/policy` is not a DAC decision: `sel_open_policy()` in `security/selinux/selinuxfs.c` calls `avc_has_perm()` for `security { read_policy }` against `SECINITSID_SECURITY`, so a root shell in a domain that lacks that permission gets `EACCES` regardless of uid — the normal case on a production device. The practical source is the precompiled policy from the image, `/system/etc/selinux/precompiled_sepolicy` or `plat_sepolicy.cil` plus the vendor pieces, after which `sesearch --allow -s untrusted_app -t <type> -c chr_file <policy>` from [SETools](https://github.com/SELinuxProject/setools) enumerates what a domain may do. [02-reachability-and-attack-surface.md](02-reachability-and-attack-surface.md) works this through properly and [09](09-privilege-escalation-to-root.md) uses it to choose a target SID.

## Glossary

- ACK — Android Common Kernel: the branch family (`android<release>-<version>`, e.g. `android14-6.1`) that Android devices actually ship, downstream of an LTS tree and carrying patches that may never reach mainline. Read it off `/proc/version`; see [01](01-vulnerability-discovery-and-patch-triage.md).
- AID — Android ID, the fixed uid/gid assignments Android layers on POSIX identity (`AID_SHELL` = 2000, `AID_SYSTEM` = 1000, `AID_INPUT` = 1004). `id` prints yours; group membership decides access to device nodes such as `/dev/uhid`.
- arbitrary read — a primitive that returns the contents of an attacker-chosen kernel address. Fuller treatment in [07](07-read-write-primitives.md).
- arbitrary write — a primitive that stores attacker-chosen data at an attacker-chosen kernel address; usually built by corrupting a pointer a legitimate code path dereferences rather than by writing directly.
- ashmem — Android's anonymous shared memory driver (`/dev/ashmem`, superseded by memfd on newer releases), notable as an allocation source reachable from an unprivileged app.
- binder — Android's IPC driver, exposed as `/dev/binder`, `/dev/hwbinder` and `/dev/vndbinder`, each gated by SELinux ([AOSP binder IPC](https://source.android.com/docs/core/architecture/hidl/binder-ipc)); a transaction is a controllable kernel allocation as well as a message.
- BTF — BPF Type Format, compact type information embedded in the kernel image and exposed at `/sys/kernel/btf/vmlinux`, with per-module blobs at `/sys/kernel/btf/<module>` ([spec](https://docs.kernel.org/bpf/btf.html)); the way to recover struct layouts on a kernel you cannot rebuild. Mode 0444, but SELinux may still refuse the read from `shell` or an app domain, in which case take the blob from the matching GKI build artifact.
- buddy allocator — the page-level allocator that manages free memory as power-of-two blocks, splitting and coalescing them ([physical memory](https://docs.kernel.org/mm/physical_memory.html)); observable through `/proc/buddyinfo`.
- cache aliasing — SLUB's merging of distinct `kmem_cache` instances with compatible size and flags into one shared cache, so objects of unrelated types share a freelist. `/sys/kernel/slab/<cache>/aliases` gives the count (root); `ls -l /sys/kernel/slab | grep ':'` names the sets. Expect none on stock GKI, which unsets `CONFIG_SLAB_MERGE_DEFAULT`. See [05](05-heap-grooming-and-spraying.md).
- capability set — the permitted, effective, inheritable, bounding and ambient bitmaps in `struct cred` that partition root's authority ([capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html)); uid 0 without `CAP_SYS_ADMIN` is still blind to `/proc/self/pagemap`.
- CFI — control-flow integrity; on Android kernels this is kCFI, a per-prototype hash checked at each indirect call site ([LWN](https://lwn.net/Articles/898040/)), which is why a corrupted function pointer typically panics rather than executes.
- `cpu_partial` — the per-cache bound on how many frozen slabs SLUB parks on the per-CPU partial list before `put_cpu_partial()` unfreezes them; it is the difference between a free that returns a page and a free that hides one. Read it at `/sys/kernel/slab/<cache>/cpu_partial` (root, mode 0400) alongside `min_partial`; see [05](05-heap-grooming-and-spraying.md) and [06](06-cross-cache-attacks.md).
- cred — `struct cred`, the refcounted credential object holding uid/gid quadruples, capability sets and the LSM blob; documented at [credentials](https://docs.kernel.org/security/credentials.html), targeted in [09](09-privilege-escalation-to-root.md).
- cross-cache — forcing a freed slab page back to the page allocator so it is re-allocated to a different `kmem_cache`, converting a UAF on one type into a type confusion with another. See [06](06-cross-cache-attacks.md).
- double free — releasing the same allocation twice, corrupting freelist bookkeeping. `CONFIG_SLAB_FREELIST_HARDENED` adds both the pointer obfuscation below and SLUB's cheap same-slot double-free check, which makes the naive version fail loudly rather than usefully; confirm it with `zcat /proc/config.gz | grep SLAB_FREELIST` (set in the arm64 `gki_defconfig`) and see [05](05-heap-grooming-and-spraying.md) for the commit history.
- enforcing mode — SELinux state in which policy denials are blocked as well as logged; `getenforce` reports it, and flipping the kernel's enforcing flag is a standard second write after credential corruption ([AOSP SELinux](https://source.android.com/docs/security/features/selinux)).
- freelist — SLUB's singly linked list of free objects within a slab, threaded through the objects themselves. With `CONFIG_SLAB_FREELIST_HARDENED` the stored `next` is XORed with a per-cache random value and with the byte-swapped address of the slot holding it, so the same pointer encodes differently in different slots; with `CONFIG_SLAB_FREELIST_RANDOM` a fresh slab's initial free order is shuffled. Both are set in the arm64 `gki_defconfig`; check yours with `zcat /proc/config.gz | grep SLAB_FREELIST`, and see [05](05-heap-grooming-and-spraying.md) for what each one does and does not stop.
- ftrace — the kernel's function tracer and the tracefs infrastructure beneath kprobe events, dynamic events and tracepoints ([documentation](https://docs.kernel.org/trace/ftrace.html)).
- GKI — Generic Kernel Image, the unified Android core kernel with SoC support pushed into loadable vendor modules behind a stable KMI ([AOSP](https://source.android.com/docs/core/architecture/kernel/generic-kernel-image)); the reason one set of offsets can cover many devices. See also KMI below.
- grooming — arranging the heap before triggering a bug so the vulnerable object lands where you intend, as opposed to simply allocating a great many objects. See [05](05-heap-grooming-and-spraying.md).
- heap feng shui — the older name for the same discipline, emphasizing deliberate hole creation and placement rather than volume; see Nikolenko's [notes](https://duasynt.com/blog/linux-kernel-heap-feng-shui-2022).
- hit rate — the fraction of attempts in which a probabilistic step lands correctly; the only honest way to describe an exploit stage, and the quantity [10](10-survivability-and-measurement.md) is about measuring.
- info leak — any disclosure of kernel data to an attacker-visible channel; a single kernel pointer is usually enough to collapse KASLR. See [04](04-kaslr-and-information-leaks.md).
- kallsyms — the kernel symbol table exposed at `/proc/kallsyms`; addresses read back as zeros unless `kptr_restrict` permits and the reader holds `CAP_SYSLOG`, so a table of zeros means restriction, not absence.
- KASAN — the kernel address sanitizer, which reports bug class, faulting access, and both allocation and free stacks for a UAF ([docs](https://docs.kernel.org/dev-tools/kasan.html)); requires a kernel built with it, so it belongs to the debug-device half of the workflow.
- KASLR — kernel address space layout randomization ([LWN, 2013](https://lwn.net/Articles/569635/)). On arm64 it is not one randomization: the kernel image's virtual slide, the module region's base, and the physical address the bootloader loads the image at are randomized separately, so a leaked text pointer collapses the image slide and nothing else. Which regions are slid and which are fixed, and which leak collapses which, is [04](04-kaslr-and-information-leaks.md).
- kmalloc-cg — the parallel set of `kmalloc-cg-N` caches serving allocations flagged `GFP_KERNEL_ACCOUNT`, that is, charged to a memory cgroup. An unaccounted spray cannot reclaim an accounted victim or the reverse, which invalidates a spray vehicle without changing its size; `grep kmalloc-cg /proc/slabinfo` shows the set exists, and the object's own `GFP_` flag at its allocation site decides which half it lands in. See [05](05-heap-grooming-and-spraying.md) and [06](06-cross-cache-attacks.md).
- kmem_cache — a slab cache: the object-size-and-constructor-specific allocator from which a given type is served, named in `/proc/slabinfo`.
- KMI — Kernel Module Interface, the set of symbols and struct layouts GKI freezes for the lifetime of a release branch so that vendor modules built against one build load on later ones. It is what makes a single offset table usable across a device family and across monthly updates; the KMI generation is the `k` field of the release string in `/proc/version` ([GKI versioning](https://source.android.com/docs/core/architecture/kernel/gki-versioning)). See [01](01-vulnerability-discovery-and-patch-triage.md).
- kprobe — a dynamic breakpoint on a kernel instruction that can log arguments, return values or memory at an address ([kprobes](https://docs.kernel.org/trace/kprobes.html), [kprobetrace](https://docs.kernel.org/trace/kprobetrace.html)); a kretprobe is the return-site variant.
- linear map — the arm64 direct mapping of all physical memory into a contiguous kernel virtual range starting at `PAGE_OFFSET = -(1UL << VA_BITS)`, so that a physical address has a computable kernel VA ([arm64 memory](https://docs.kernel.org/arch/arm64/memory.html)). It is not slid by KASLR, because linear-region randomization was removed from arm64 outright; with `VA_BITS` fixed at build time the only unknown in `__phys_to_virt()` is `PHYS_OFFSET`. [04](04-kaslr-and-information-leaks.md) has the commit, the consequence — a chain confined to linear aliases needs no leak — and the arithmetic.
- LSM — Linux Security Modules, the hook framework through which SELinux and friends intercept operations ([index](https://docs.kernel.org/admin-guide/LSM/index.html)); its hooks are where a policy decision is made and therefore where a corrupted state flag has effect.
- migratetype — the buddy allocator's classification of a free block as unmovable, movable, reclaimable and so on; free lists and per-CPU pagesets are kept per `(migratetype, order)` pair, so a reclaim allocation of the wrong migratetype never sees the page you freed however well the order matches. `/proc/pagetypeinfo` (root, mode 0400) prints the free-block counts split this way, and the `mm_page_alloc` tracepoint carries a `migratetype=` field. See [06](06-cross-cache-attacks.md).
- msg_msg — the System V message object, allocated by `alloc_msg()` in `ipc/msgutil.c` and the canonical elastic spray vehicle: a fixed header plus a caller-chosen payload length, so `msgsnd()` can be aimed at almost any `kmalloc-N` cache and `msgrcv()` reads the content back. `MSG_COPY` makes that read-back non-destructive but is conditional on `CONFIG_CHECKPOINT_RESTORE`, which Android's arm64 `gki_defconfig` does not set. See [05](05-heap-grooming-and-spraying.md), [06](06-cross-cache-attacks.md) and [07](07-read-write-primitives.md).
- MTE — Arm Memory Tagging Extension, hardware memory tagging that turns many heap corruptions into immediate faults ([kernel documentation](https://docs.kernel.org/arch/arm64/memory-tagging-extension.html)). Whether it is on decides whether a sloppy primitive is survivable, and it is three separate questions with three separate answers. Compiled in: `zcat /proc/config.gz | grep -E 'KASAN_HW_TAGS|ARM64_MTE'` — the arm64 `gki_defconfig` sets `CONFIG_KASAN=y` and `CONFIG_KASAN_HW_TAGS=y`, so MTE-based KASAN is built into a stock GKI kernel. On at runtime for kernel allocations, which is the answer that governs whether corrupting a kernel object faults: HW_TAGS KASAN needs both a CPU that implements MTE and the boot-time switches, so read `cat /proc/cmdline` for `kasan=off|on` and `kasan.mode=sync|async|asymm` ([KASAN documentation](https://docs.kernel.org/dev-tools/kasan.html)); [01](01-vulnerability-discovery-and-patch-triage.md) and [06](06-cross-cache-attacks.md) both record the target as built in but inert. Available to userspace: `getauxval(AT_HWCAP2) & HWCAP2_MTE`, which says the CPU has the feature and says nothing about the kernel's own allocations.
- OOB access — out-of-bounds read or write: touching memory outside an allocation's bounds, typically through an unvalidated index or a length computed from attacker-controlled input.
- order-N page — a buddy-allocator block of 2^N contiguous pages; a slab cache's `pagesperslab` tells you which order its backing allocation comes from, which is what a cross-cache must match.
- per-CPU pageset — the small per-CPU free-page cache (PCP) the buddy allocator drains through; a page freed to it is reused LIFO on that CPU and does not appear in `/proc/buddyinfo` until the list drains, which is why cross-cache work is CPU-affine. The interception has an order bound: `pcp_allowed_order()` admits orders up to `PAGE_ALLOC_COSTLY_ORDER` (3), plus `pageblock_order` under transparent huge pages, and a higher-order page goes straight to the buddy allocator and does show up in buddyinfo immediately. Which side of that line your victim cache falls on comes from `pagesperslab` in `/proc/slabinfo` or `/sys/kernel/slab/<cache>/order`. See [06](06-cross-cache-attacks.md).
- PFN — page frame number, a physical address divided by page size; readable per-virtual-page from `/proc/<pid>/pagemap`, but zeroed without `CAP_SYS_ADMIN` ([pagemap](https://docs.kernel.org/admin-guide/mm/pagemap.html)). The capability is evaluated against the opening process's credentials, not the reading one's: `pagemap_read()` sets `pm.show_pfn = file_ns_capable(file, &init_user_ns, CAP_SYS_ADMIN)`, and `file_ns_capable()` tests `file->f_cred`, captured at `open()`. An exploit that patches its own cred to gain `CAP_SYS_ADMIN` and then reads an fd it already held still gets zeros; reopen `/proc/self/pagemap` after any credential change. `cves/lib/addr/pagemap.h` opens and closes the file on every lookup, so it never carries a stale `f_cred` across one.
- PHYS_OFFSET — `memstart_addr`, the physical address at which usable RAM begins on a given board; PFNs from pagemap are absolute, so any conversion to a `vmemmap` index must subtract it. It is a per-board constant rather than a per-boot one, but it is measured rather than assumed: root can read the first `System RAM` resource out of `/proc/iomem`, and without root it is recovered by round-tripping a mapping whose kernel VA you already know through `/proc/self/pagemap` with the conversions in [04](04-kaslr-and-information-leaks.md), or, where its address is known, by reading `memstart_addr` itself with the kprobe `@ADDR` fetch above.
- pipe_buffer — the descriptor array behind a pipe (`struct pipe_buffer`: a `struct page *`, an offset, a length and a `const struct pipe_buf_operations *`), allocated as one `kmalloc` block sized by the pipe's ring capacity, which `fcntl(F_SETPIPE_SZ)` sets. It is the project's central write target because corrupting `page`, `offset` and `len` redirects `read`/`write` at an attacker-chosen physical page, and because the array's size is caller-chosen it doubles as a cache-selectable spray vehicle. `fs/pipe.c` allocates it with `GFP_KERNEL_ACCOUNT`, so it lands in `kmalloc-cg-*` rather than the plain caches. Appears in [01](01-vulnerability-discovery-and-patch-triage.md), [05](05-heap-grooming-and-spraying.md), [06](06-cross-cache-attacks.md), [07](07-read-write-primitives.md) and [10](10-survivability-and-measurement.md).
- primitive — a repeatable capability with a stated contract (read eight bytes here, write these bytes there, free this object now), as distinct from the bug that produced it. [07](07-read-write-primitives.md) is about the conversion.
- pstore — the persistent-store subsystem that preserves console and dmesg records across a reboot, backed by ramoops on Android ([documentation](https://docs.kernel.org/admin-guide/ramoops.html)); read a known path such as `/sys/fs/pstore/console-ramoops-0` directly, since listing the directory may itself be denied by policy.
- race window — the interval between a check and a use, or between two operations on shared state, during which an attacker's action changes the outcome; widening it deliberately is the subject of [08](08-triggering-races-reliably.md).
- RCU — read-copy-update, the deferral mechanism that lets readers proceed without locks by postponing reclamation until a grace period elapses ([McKenney](https://lwn.net/Articles/262464/)). Two distinct uses of it change exploitation timing in opposite directions, and conflating them produces a third mechanism that does not exist. Object-level: a subsystem calls `call_rcu()` on the object, so the `kmem_cache_free()` itself runs later in a callback — the object is still allocated throughout the interval, and the callback may execute on a CPU other than the one that queued it. Slab-level: see `SLAB_TYPESAFE_BY_RCU` below, where the object slot comes back immediately and only the page is held. [06](06-cross-cache-attacks.md) works both through on the target kernel.
- reclaim — in exploitation, re-allocating the memory a freed object occupied with attacker-controlled content; in kernel terminology the same word means eviction of pages under memory pressure, and the two meanings collide constantly.
- refcount overflow — driving an object's reference count past its limit so a later decrement frees an object still in use; `refcount_t` saturates and warns rather than wrapping, which converts many of these into denial of service.
- seccomp-bpf — per-process syscall filtering with BPF programs, whose return actions range from `SECCOMP_RET_ERRNO` to `SECCOMP_RET_KILL_PROCESS` ([documentation](https://docs.kernel.org/userspace-api/seccomp_filter.html)); on Android it constrains app processes and shapes which syscalls an in-process payload may use.
- SELinux domain — the type label on a process, such as `untrusted_app` or `shell`, that selects which policy rules apply to it; `id -Z` prints yours. See [02](02-reachability-and-attack-surface.md).
- SID — the runtime security identifier the kernel uses internally for a security context, mapped from the context string by the policy database.
- slab — both a page-backed chunk of memory carved into equal-size objects and, loosely, the whole object-allocation layer above the page allocator.
- `SLAB_TYPESAFE_BY_RCU` — a cache flag under which a freed object's slot is handed straight back for reuse, while the slab *page*'s return to the buddy allocator is deferred through `call_rcu(&slab->rcu_head, rcu_free_slab)`. For an exploit the consequences are opposite to object-level `call_rcu`: same-cache reuse is immediate, cross-cache page delivery is not. Settle it per cache with `cat /sys/kernel/slab/<cache>/destroy_by_rcu` (root, mode 0400), which `destroy_by_rcu_show()` in `mm/slub.c` prints as 1 exactly when the flag is set. See [06](06-cross-cache-attacks.md).
- SLUB — the slab allocator Linux actually uses: per-CPU active slabs, freelists threaded through free objects, metadata in the page descriptor, and cache merging ([design notes](https://lwn.net/Articles/229984/), [users guide](https://docs.kernel.org/admin-guide/mm/slab.html)).
- spray — allocating many objects of a chosen type to fill freed space or to make a target land at a predictable place; distinguished from grooming by intent, not by mechanism.
- SPL — security patch level, the `ro.build.version.security_patch` property a device claims; a claim about intent, which the kernel banner may contradict.
- system_server — the privileged Android system process hosting most framework services; a code-execution bug there yields the `system` uid and a large SELinux domain without touching the kernel.
- task_struct — the per-thread kernel descriptor holding scheduling state, the `mm`, the file table and the pointer to `struct cred`; the object you traverse from when escalating.
- TOCTOU — time-of-check to time-of-use: a bug in which state validated at one instant is used at a later one, after an attacker has changed it.
- tracefs — the filesystem, normally at `/sys/kernel/tracing`, through which ftrace, kprobe events and tracepoints are configured and read; write access is the gate on most live observation.
- type confusion — treating memory as one type when it holds another, so field offsets are reinterpreted; the standard consequence of a successful cross-cache.
- UAF — use-after-free: a dangling reference dereferenced after the object was released, exploitable by placing a controlled object in the freed space before the dereference.
- uhid — the userspace HID driver at `/dev/uhid`, which lets a process create a virtual HID device and drive the kernel HID stack; reachability depends on group membership and SELinux, and where it exists it turns transport-specific driver bugs into locally triggerable ones.
- vmemmap — the virtual array of `struct page` descriptors indexed by PFN relative to the start of RAM, so that a physical page's descriptor has a computable address.

## Instruments

- `zcat /proc/config.gz | grep -E 'DEBUG_INFO_BTF|SLUB_DEBUG|SLAB_MERGE|SLAB_FREELIST|KASAN|PROC_KCORE|IKCONFIG'` — which of the other instruments exist on this build, and which mitigations are compiled in. Unprivileged (mode 0444), needs `CONFIG_IKCONFIG_PROC`; without it, the published `gki_defconfig` for the branch in `/proc/version` is a claim about the branch rather than the build.
- `adb shell cat /proc/version` and `getprop ro.build.version.security_patch` — the kernel's own identity versus the vendor's claimed patch level; unprivileged.
- `adb pull /sys/kernel/btf/vmlinux` then `pahole -F btf -C <struct> ./vmlinux.btf` — per-member offsets, sizes and padding for this exact build; mode 0444 but SELinux may still refuse the on-device read, needs `CONFIG_DEBUG_INFO_BTF` and dwarves on the host. Module types are in `/sys/kernel/btf/<module>`, not the vmlinux blob.
- `bpftool btf dump file vmlinux.btf format c` — the whole type universe as compilable C when `pahole` is unavailable; same privilege.
- `cat /proc/slabinfo`, `slabtop -o -s c` — cache names, object size, objects and pages per slab; root-only, mode 0400 on a SLUB kernel, since `SLABINFO_RIGHTS` is 0600 only under `CONFIG_SLAB`. Absent entirely unless the build sets `CONFIG_SLAB` or `CONFIG_SLUB_DEBUG`, so `ENOENT` and `EACCES` mean different things.
- `ls -l /sys/kernel/slab | grep ':'` — the merge sets as symlinks (`<name> -> :A-0001280`), readable without root because the targets are; `cat /sys/kernel/slab/<cache>/aliases` gives the count `s->refcount - 1` and needs root, since `SLAB_ATTR_RO` is mode 0400. Both need `CONFIG_SYSFS` slab support. Expect 0 on stock GKI, which unsets `CONFIG_SLAB_MERGE_DEFAULT`.
- `cat /proc/buddyinfo`, `cat /proc/zoneinfo` — free blocks per order per zone, and watermarks plus per-CPU pageset `count`/`high`/`batch`; both mode 0444.
- `cat /proc/pagetypeinfo` — the same free-block counts split by migratetype, so you can see whether the order you need is on an unmovable list at all; root, mode 0400.
- `cat /proc/<pid>/pagemap` — virtual page to PFN, PFN in bits 0–54 and present in bit 63; PFN reads zero without `CAP_SYS_ADMIN`, tested once against `file->f_cred` at `open()`, so reopen the file after any credential change.
- `echo 'p:peek0 <sym> val=@<addr>:u64 chk=@<known>:u64' > /sys/kernel/tracing/kprobe_events` — an eight-byte read at a chosen address when the probe fires; needs tracefs write access. Neither failure mode is reported: check `kprobe_profile` for a nonzero `nhit` before believing any line, because a missing record means the site was never reached rather than zero, and carry the `chk=` control fetch, because a faulting fetch leaves its slot unwritten and prints whatever the ring-buffer record already held. Clear `trace` before arming and `kprobe_events` after.
- `drgn -k` / `crash <namelist> <dump>` — scripted traversal of live or postmortem kernel structures. `drgn -k` needs `CONFIG_PROC_KCORE`, which the arm64 `gki_defconfig` does not set, plus root and DWARF or BTF; so both are bench instruments for a dump, a Cuttlefish instance or a lab kernel, never the phone.
- `cat /proc/kallsyms` — runtime symbol addresses; all-zero output means `kptr_restrict`, at which point BTF is the offset fallback.
- `cat /sys/fs/pstore/console-ramoops-0` — the console log preserved across a panic-reboot; read the path directly, as listing the directory may be denied.
- `getenforce`, `id -Z`, `ls -Z <node>` — enforcement state, your own domain, and a target node's label; all unprivileged.
- `sesearch --allow -s <domain> -t <type> -c <class> <policy>` — the rules permitting one domain to act on one type; needs a policy file. `/sys/fs/selinux/policy` is gated by the SELinux `security { read_policy }` permission rather than by uid, so root may still be refused; the reliable source is the image's `precompiled_sepolicy` or `plat_sepolicy.cil` plus the vendor pieces.
- `bpftrace -l 'kprobe:*<pattern>*'` and `bpftrace -e 'kprobe:fn { ... }'` — probe enumeration and struct-aware reads at a probe point; needs BPF, BTF and root ([bpftrace](https://bpftrace.org/)).
- `vmlinux-to-elf <image> vmlinux.elf` then `readelf -s` / `objdump -d` — symbols and disassembly reconstructed from a stripped kernel image ([tool](https://github.com/marin-m/vmlinux-to-elf)); offline, no device access needed.

## Grounded in this project

Several of the instruments above exist here as shared, reusable scripts rather than as ad-hoc invocations. `cves/lib/tools/kprobe.sh` wraps the kprobe-event interface with the two properties that separate an instrument from an accident — every probe removed and tracing state restored on exit, and every probe filtered to one process where a filter is possible. `cves/lib/tools/symbol-shape.sh`, `cves/lib/tools/module-shape.sh` and `cves/lib/tools/binary-strings.sh` are the three patch-presence tests, sharing one exit-status contract in which "inconclusive" is a first-class outcome rather than a collapsed guess; `cves/lib/tools/README.md` states that contract. The unprivileged symbol-table queries and their masking-aware error handling are `cves/lib/base/kallsyms.h`; the pagemap and physical-address instruments are `cves/lib/addr/pagemap.h` and `cves/lib/addr/physlayout.h`; the privileged ground-truth read used to check unprivileged primitives is `cves/lib/rw/kprobe_read.h`. `runner/scripts/dump-boot-image.sh` pulls the running kernel's own `Image` off the device, which is how symbols that are static or inlined — invisible to both kallsyms and BTF — are recovered.
